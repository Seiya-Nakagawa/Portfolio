## 1. 概要

Issue #189 の対応。商用化の PR のレビューで見送った指摘のうち、流量制限の負荷（実測が必要）を除く
10 項目を対応する。設計は [基本設計書](../02.design/DESIGN.md) の 4.3・4.3.1・4.12・4.13・4.14・5.3.2・7.2・7.3 を参照する。

## 2. 前提条件

- 構築手順書 28（死活監視）・27（流量制限）が適用済みであること

## 3. 手順

### 3.1. データベースの追加

マイグレーション `0025_released_usernames_job_runs` で次のテーブルを追加する。

| テーブル | 内容 |
| -------- | ---- |
| `released_usernames` | 変更・退会で解放したユーザー名の予約（ユーザー名・解放日時・解放したユーザーの id） |
| `job_runs` | 定期ジョブの最終成功時刻。移行時に `daily_maintenance` を現在時刻で初期化する |

### 3.2. 共通マスタへの統合と種類のロック

1. `registry.merge_custom_skills_into_master` で、共通マスタの項目と同じ種類・名前の独自スキル項目の使用実績を
   共通マスタへ付け替え、独自スキル項目を削除する。運営者の項目の追加・変更と、`import_skill_master` から呼ぶ
2. 独自スキル項目の保存は、独自スキル項目の行をロックする前に種類の行をロックし（`_lock_categories`）、
   種類の存在をロック読み取りで確認する。種類の名称変更・削除と直列化するため

### 3.3. 退会の再認証とユーザー名の予約

1. ログイン時にセッションへ認証時刻を記録する（`user_logged_in` の受信関数）。退会の API は
   `RECENT_LOGIN_MINUTES`（10 分）以内でなければ 403（`reauth_required`）を返す
2. 画面は 403 を受けると、ログアウトして再ログインする案内を表示する（再ログイン後は登録画面へ戻る）
3. ユーザー名の変更・退会で、旧ユーザー名を `released_usernames` に記録する。予約の期間は
   `USERNAME_RESERVATION_DAYS`（90 日）で、解放した本人は取り直せる。期限切れの行は日次の整理処理で削除する
4. 運営者のユーザー名を変更する場合は、`LEGACY_REDIRECT_USERNAME`（`k8s/configmap.yaml`）も同じリリースで更新する

### 3.4. 画像の配信

1. `/media/` の応答に `Cache-Control: private, no-cache` を付ける
2. 移行前の旧パス `/media/works/{ファイル名}` は、`works.thumbnail` から所有者を特定し、新しいパスと同じ条件で配信する。
   `migrate_media` が完了し、旧パスの参照がなくなった後に廃止してよい

### 3.5. 利用状況の加算

`usage.increment` を、セーブポイントの内側で行い、失敗しても例外を出さずに警告ログへ記録する。
退会・サインアップのトランザクションも巻き込まない。

### 3.6. 死活監視

1. `health.py` の判定を、DB の読み取り可否と日次の整理処理の最終成功時刻（26 時間以内）に変更する。
   5xx の件数の計数（`ServerErrorCountMiddleware`）と設定 `HEALTH_MAX_SERVER_ERRORS`・`HEALTH_ERROR_WINDOW_MINUTES` を廃止する
2. `daily_maintenance` が成功した時刻を `job_runs` に記録する。失敗した場合は記録を更新しない
3. `.github/workflows/health-check.yml` で、200 かつ本文が `ok` であることを確認する。異常時は
   ラベル `monitoring` の Issue を起票（または追記）し、復旧時にコメントしてクローズする
   （ワークフローの権限は `issues: write`）

### 3.7. ローカルでの動作確認

```bash
uv run ruff check .
uv run ruff format --check .
uv run python manage.py test --settings=config.settings.test
```

### 3.8. 本番への適用

1. マージ後の CD の完了後、`https://skillsheet.technohonesty.com/healthz` が 200（`ok`）を返すことを確認する
2. GitHub の Actions 画面から「Health Check」を手動実行し、成功すること（異常の Issue が起票されないこと）を確認する
3. `kubectl -n app-prod get cronjob portfolio-daily-maintenance` で、次回の実行後に `job_runs` の時刻が更新されることを確認する
   （初回の実行までは移行時の時刻が使われる）
4. 画像（公開中・旧パスの画像）の表示と、応答の `Cache-Control: private, no-cache` を確認する
5. 実在するアカウントで、退会の画面が再ログインを案内することを確認する（退会は実行しない）
