## 1. 概要

Issue #166 の対応。django-allauth で Google・GitHub によるサインアップ・ログインを実装し、
パスワードによるログインを廃止する。サインアップ時のユーザー名入力と規約への同意、規約改定時の再同意、
利用停止中のログイン拒否を実装する。設計は
[基本設計書 4.12](../02.design/DESIGN.md#412-ユーザーとアカウント)・
[5.2.3](../02.design/DESIGN.md#523-ログインサインアップ)・
[5.3.3](../02.design/DESIGN.md#533-サービス共通) を参照する。

| 区分 | 内容 |
| ---- | ---- |
| 依存パッケージ | `django-allauth[socialaccount]`（65 系）を追加する |
| DB | allauth のテーブル（`account_*`・`socialaccount_*`）がマイグレーションで作成される |
| 環境変数 | `GOOGLE_CLIENT_ID`・`GOOGLE_CLIENT_SECRET`・`GITHUB_CLIENT_ID`・`GITHUB_CLIENT_SECRET`。値の作成と OCI Vault への登録は別の構築手順書で行う |

## 2. 前提条件

- [19 構築手順書](19_データの所有者の追加と既存データの移行.md) のマイグレーションが適用済みであること
- OAuth クライアントを作成済みであること（開発用の ID・シークレットを `.env` に設定する）

## 3. 手順

### 3.1. ローカルでの動作確認

```bash
docker compose -f webapp/docker-compose.yml up -d db
```

- 確認用の MySQL を起動する

```bash
uv run python manage.py migrate
```

- allauth のテーブルを含むマイグレーションを適用する

```bash
uv run python manage.py runserver
```

1. `/login/` に Google・GitHub のボタンのみが表示され、パスワード欄がないことを確認する
2. 未登録の Google アカウントでログインし、サインアップ画面でユーザー名と規約への同意を入力して登録できることを確認する
3. 規約の同意記録（`user_profiles`）と登録数（`usage_daily`）が記録されることを確認する
4. `TERMS_VERSION` を変更して再読み込みし、再同意画面へ誘導されることを確認する
5. ユーザーの `is_active` を偽にして、ログインが拒否され、既存のセッションが無効になることを確認する

### 3.2. 運営者のメールアドレスの設定

運営者の既存ユーザーを初回の Google ログインで紐づけるため、メールアドレスを運営者の Google アカウントのものに
合わせる。リリース後、最初のログインより前に実施する。

```bash
ssh oci-server
```

```bash
kubectl -n app-prod exec -it deploy/portfolio-web -c web -- python manage.py shell
```

- 運営者のユーザーの `email` を Google アカウントのメールアドレスに更新する（シェル内で
  `User.objects.filter(is_staff=True).update(email="{Google アカウントのメールアドレス}")` を実行する）

### 3.3. 適用後の確認

1. 運営者が Google でログインでき、既存のユーザーに紐づくこと（新規のサインアップ画面が表示されないこと）
2. `/admin/login/` が `/login/` へ転送されること
