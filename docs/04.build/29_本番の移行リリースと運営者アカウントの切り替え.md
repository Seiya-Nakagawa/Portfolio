## 1. 概要

Issue #175 の対応。商用化の変更を本番へリリースし、単一ユーザー構成で蓄積した既存データを運営者のユーザーへ
移行する。移行の方式は [基本設計書 4.15](../02.design/DESIGN.md#415-既存データの移行)、旧 URL の扱いは
[基本設計書 6.5](../02.design/DESIGN.md#65-旧-url-からのリダイレクト) を参照する。

各機能の実装手順は次の構築手順書を参照し、本書では本番への適用と切り替えの作業のみを扱う。

| 所有者の追加と既存データの移行 | [19](19_データの所有者の追加と既存データの移行.md) |

## 2. 前提条件

- 21 の手順が完了し、OCI Vault の 4 つのシークレットに本番の値が登録され、`portfolio-secrets` が同期していること
- 運営者の Google アカウントを、Google の OAuth 同意画面のテストユーザーに追加していること
  （公開ステータスが「テスト」の間）
- 運営者のユーザーの `email` が、運営者が Google ログインに使うアカウントのメールアドレスと一致していること
- 作業端末から `ssh oci-server` で接続できること

## 3. 手順

### 3.1. 移行前のダンプ取得

1. 実績 DB のダンプを手動で取得する

   ```bash
   ssh oci-server
   ```

   ```bash
   sudo systemctl start mysql-backup.service
   ```

   - 日次のバックアップ（`mysql-backup.timer`）と同じ処理を手動で実行し、OCI Object Storage へアップロードする

2. 取得結果を確認する

   ```bash
   systemctl status mysql-backup.service --no-pager
   ```

   - `status=0/SUCCESS` であること。`portfolio` のバックアップ完了がジャーナルに出ていること

   ```bash
   journalctl -u mysql-backup.service -n 12 --no-pager
   ```

3. 運営者のユーザーが 1 人であることを確認する

   ```bash
   kubectl -n app-prod exec deploy/portfolio-web -c web -- python manage.py shell -c "from django.contrib.auth import get_user_model; print(get_user_model().objects.count())"
   ```

   - 出力が `1` であること。`1` 以外の場合、`0022_assign_owner` は移行を中止する

4. 運営者の `email` を設定する

   ```bash
   kubectl -n app-prod exec deploy/portfolio-web -c web -- python manage.py shell -c "from django.contrib.auth import get_user_model; u = get_user_model().objects.get(); u.email = '{運営者の Google アカウントのメールアドレス}'; u.save(update_fields=['email'])"
   ```

   - 上記の `{…}` を実際の値に置き換える
   - 初回の Google ログインで、検証済みのメールアドレスが一致するユーザーに外部アカウントが紐づく。
     一致しないと新規ユーザーが作られ、既存データに届かない

### 3.2. 移行リリース

1. 21 の完了後、積み重ねた PR を親から順にマージする。マージのたびに `deploy.yml` の CD が実行されるため、
   各 CD の完了を確認してから次へ進む

   ```bash
   gh run watch
   ```

   - 失敗した場合は、次のマージに進まず 3.6 に従う

### 3.3. データ移行と画像の移動の確認

1. マイグレーションの適用状況を確認する

   ```bash
   kubectl -n app-prod exec deploy/portfolio-web -c web -- python manage.py showmigrations portfolio
   ```

   - すべてに `[X]` が付いていること

2. 画像の移動を確認する

   ```bash
   kubectl -n app-prod exec deploy/portfolio-web -c web -- python manage.py migrate_media
   ```

   - 再実行して `移動 0 件` かつ `実体なし 0 件` になること

3. 外部アカウント認証の資格情報が同期していることを確認する

   ```bash
   kubectl -n app-prod get externalsecret portfolio-secrets
   ```

   - `STATUS` が `SecretSynced`、`READY` が `True` であること

### 3.4. 運営者の Google ログインの紐づけとユーザー名の設定

1. `https://skillsheet.technohonesty.com/login/` を開き、「Google でログイン」を選ぶ
2. 運営者の Google アカウントで認可する
   - 既存の運営者のユーザーに紐づき、サインアップ画面に進まないこと
3. 利用規約とプライバシーポリシーに同意する画面が出た場合は、同意する
4. アカウント画面でユーザー名を設定し、公開設定を「公開」にする
5. 運営者のユーザー名を、旧 URL の転送先として設定する（22 の 3.3 に従う）

### 3.5. 旧 URL のリダイレクトと公開ポートフォリオの確認

1. 旧 URL が公開ポートフォリオへ転送されることを確認する

   ```bash
   curl -sI https://technohonesty.com/portfolio/
   ```

   - `HTTP/2 301` と、`location` が `https://skillsheet.technohonesty.com/u/{運営者のユーザー名}/` であること

2. `https://skillsheet.technohonesty.com/u/{運営者のユーザー名}/` を開き、スキル・実績・画像が表示されること
3. ログインせずに、運営者以外の非公開ユーザーの画像の URL が 404 になること

### 3.6. 失敗時の復旧

1. 次のマージを止める
2. 移行に失敗した場合は、3.1 で取得したダンプから実績 DB を戻す
3. 復旧後、原因を修正した PR を作成し、3.2 からやり直す
