## 1. 概要

Issue #174 の対応。ヘルスチェックのエンドポイントと、GitHub Actions による 15 分ごとの定期確認を作成し、
gunicorn のワーカー数と Pod のリソース上限を見直す。設計は
[基本設計書 7.2](../02.design/DESIGN.md#72-死活監視) を参照する。

## 2. 前提条件

- 流量制限の回数のテーブル（構築手順書 27）が適用済みであること（5xx の件数を同じテーブルに数える）

## 3. 手順

### 3.1. ヘルスチェックのエンドポイント

1. `webapp/portfolio/health.py` に、5xx の計数と、DB 接続・直近の 5xx 件数による判定を実装する
2. `ServerErrorCountMiddleware` で 5xx の応答を数える（ヘルスチェック自身の 503 は数えない）
3. `/healthz`（認証不要）が、正常なら 200（`ok`）、異常なら 503（`ng`）を返す。応答に件数・構成などは含めない
4. しきい値は `config/settings/base.py` の `HEALTH_MAX_SERVER_ERRORS`（10 件）・`HEALTH_ERROR_WINDOW_MINUTES`（10 分）で定義する

### 3.2. 定期実行のワークフロー

`.github/workflows/health-check.yml` を作成する。15 分ごと（と手動実行）に `/healthz` を確認し、
200 以外または応答がない場合は 20 秒間隔で最大 3 回再確認した後、ワークフローを失敗させる。
失敗は GitHub の通知（メール）で運営者へ届く。

### 3.3. gunicorn と Pod のリソース

1. `webapp/Dockerfile` に `WEB_CONCURRENCY=2` を設定し、gunicorn を 2 ワーカーで動かす
2. `k8s/web.yaml` の resources を、requests: CPU 200m・メモリ 384Mi、limits: CPU 1・メモリ 1536Mi に変更する
   （PDF の生成を 2 ワーカーが同時に行い、ワーカー自体の使用量が加わっても収まるようにする）
3. `k8s/web.yaml` の readinessProbe に `timeoutSeconds: 10`・`failureThreshold: 6` を設定する
   （ワーカーが PDF の生成で埋まっている間の応答の遅れだけでは、Service から外れないようにする）

### 3.4. ログの確認

アプリケーションのコードにログ出力はなく、Django の既定のログと gunicorn（アクセスログは無効）のみである。
`portfolio.tests.test_health.NoPersonalDataInLogsTests` で、画面の表示・職務経歴書の生成・エラー発生時に
メールアドレスがログに出力されないことを確認している。

### 3.5. ローカルでの動作確認

```bash
uv run python manage.py test portfolio.tests.test_health --settings=config.settings.test
```

### 3.6. 本番への適用

1. マージ後の CD の完了後、`https://skillsheet.technohonesty.com/healthz` が 200 を返すことを確認する
2. GitHub の Actions 画面から「Health Check」を手動実行し、成功することを確認する
3. GitHub の通知設定で、Actions の失敗通知がメールで届くようになっていることを確認する
4. `kubectl top pod -n app-prod` で、Pod のメモリ使用量が上限に収まっていることを確認する
